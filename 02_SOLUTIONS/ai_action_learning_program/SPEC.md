# AI実践伴走プログラム（Action Learning）仕様書
## STEP2: CONVERGENCE の成果物

**入力**：`01_DIAGNOSTICS/LATENT_NEEDS_DIAGNOSIS.md`（4部門の真の潜在ニーズ）
**統合の構図**：Muskの「ゼロベース構想（最速で1/10工程を実現する学習設計とは何か）」と、Ohnoの「現地現物の現実（現場の時間・データ制約）」を戦わせ、実行可能な最速プロトタイプとして本プログラムを設計した。
**対象範囲**：機械学習・深層学習（生成AIは本プログラムのスコープ外）

---

## 1. 設計原則（何を捨てたか）

過去5年の教育がアルゴリズム講義・ツール操作研修中心で定着しなかったという診断（`LATENT_NEEDS_DIAGNOSIS.md` §3）を受け、以下を明確に**やらない**。

### Not to doリスト
1. **座学中心の一律カリキュラムはやらない**。全部門共通のPython/機械学習講座は開催しない。
2. **汎用データセット・教材データは使わない**。参加者は必ず自部門の実データ・実案件を持ち込む。
3. **生成AI（LLM等）はスコープに含めない**。本プログラムは分類・予測・異常検知等の機械学習・深層学習に限定する。
4. **参加率・受講満足度をKPIにしない**。評価は現場KPIの改善のみで測る（詳細は§5）。
5. **精度100%・完璧なモデルを目指さない**。現状比で意思決定の質が改善すれば合格とし、過剰品質への工数投下（Ohnoの言う「作りすぎのムダ」の学習版）を禁止する。
6. **暗黙知の形式知化を省略した状態でモデリングに進まない**。フェーズ0を飛ばしてフェーズ1に進むことを禁止する。

## 2. プログラム全体構成（1コホート = 12週間）

```
Phase 0: 現場現物診断        (2週間) … 実データ棚卸し・暗黙知ヒアリング・KPI合意
Phase 1: 最小構成プロトタイプ (4週間) … 1/10工程を目指すミニマムモデルの構築
Phase 2: 現場実装・評価       (4週間) … 実業務に戻して運用、精度と業務KPIを両方計測
Phase 3: 標準化・スキル化     (2週間) … SKILLS/へのテンプレート化、他部門展開設計
```

参加単位は**部門ごとの実課題（テーマ）単位**とし、各テーマに担当者2〜4名＋テーマオーナー（現場責任者）を配置する。全社一律の「クラス」は編成しない。

### Phase 0｜現場現物診断（Ohno主導）
- 対象業務の実データを持ち込み、**現地現物で**「何を判断基準にしているか」を暗黙知ヒアリングにより言語化する（例：ベテラン検査員の良否判断の言語化、生産技術者の異常兆候の言語化）。
- テーマオーナーと伴走コーチが、成功の定義＝**現場KPI（工数削減、不良流出件数、予測誤差率等）**を1つに合意する（Drucker要件：測定可能な成果を最初に定義しない限り次フェーズに進まない）。
- 成果物：`01_DIAGNOSTICS/` に案件別の診断メモ（ラベルの有無、データ量、暗黙知の言語化結果）を追記。

### Phase 1｜最小構成プロトタイプ（Musk×Ohno CONVERGENCE）
- 「今の工程・判断ステップを1/10にするなら、理論上どこまで削れるか」をMusk型のゼロベース設計で発想し、Ohno型の「現場でこの案は本当に成立するか」で即座に検証する、を毎週繰り返す。
- 既存の完成された教材ではなく、参加者が持ち込んだ実データにその場で伴走コーチと向き合う「1課題1週間サイクル」の反復。
- 成果物：`02_SOLUTIONS/<テーマ名>/` にプロトタイプコード・BPR比較図（Before/After工程図）を格納。

### Phase 2｜現場実装・評価（Ohno×Drucker）
- プロトタイプを実際の業務フローに組み込み、現場で稼働させる（PoC止まりを許さない）。
- Phase 0で合意したKPIの改善幅を実測する。効果が出ない場合は「なぜなぜ分析」で真因を再診断し、Phase1に差し戻す。
- 責任構造（モデルが誤判定した場合の対応フロー・誰が最終判断するか）をこの段階で明文化する（Drucker要件、`LATENT_NEEDS_DIAGNOSIS.md` で特定した「責任の所在不明」への恐怖への直接対応）。

### Phase 3｜標準化・スキル化（Nadella主導）
- 成果が実証されたプロンプト・前処理ロジック・モデル構成・BPR手順を、他部門がオンデマンドで使える形に整形し `SKILLS/` へ登録する（登録プロセスは `SKILLS/_INTAKE_PIPELINE.md` を参照）。
- 「使うべきでないケース」を含めて明文化し、過度な一般化（万能ツール化）を防ぐ。
- テーマオーナーが自部門内での横展開計画（誰が次に使うか）を1件以上specifyすることを卒業条件とする。

## 3. 部門別テーマ例（Phase 0で正式決定）

`LATENT_NEEDS_DIAGNOSIS.md` の真の潜在ニーズに直結するテーマを初期仮説として提示する。実テーマはPhase 0の現場診断で確定する。

| 部門 | 初期テーマ仮説 | 直接対応する潜在ニーズ |
|---|---|---|
| 製造 | ベテラン良否判断の形式知化 → 画像／センサーベース良否判定モデル | 暗黙知の未形式知化、代替への恐怖（→「代替」ではなく「本人の基準をモデル化する」形にすることで恐怖を協働に転換） |
| 技術 | 実験データパイプラインの標準化＋物性・寿命予測モデル | 前処理の重複によるロス、少数データでの手法選定の実践知不足 |
| 生産技術 | 不均衡データ対応の異常検知・予知保全モデル＋ライン間データ標準化 | クラス不均衡という現実と教育内容の不一致、ライン間の構造的ロス |
| 営業 | 受注データ品質改善＋需要予測・受注確度モデル | データ資産そのものの欠如、勘の否定への恐怖（→予測を「意思決定支援」として位置づけ、代替ではなく武器として設計） |

## 4. 体制（役割定義）

| 役割 | 人数目安 | マンデート | ボード上の対応レンズ |
|---|---|---|---|
| テーマオーナー（現場責任者） | テーマごと1名 | KPI合意・責任構造の最終決定・横展開の意思決定 | Drucker |
| AI伴走コーチ | 参加者4〜6名に1名 | 週次伴走、心理的安全性の担保、恐怖の言語化と対処 | Nadella |
| 技術メンター | コホートに1〜2名 | プロトタイプのアーキテクチャ・手法選定のレビュー | Musk |
| 現場検証パートナー | テーマごと1名 | Phase0・Phase2での現地現物検証、なぜなぜ分析のファシリテーション | Ohno |

伴走コーチ・技術メンターは初期は情報システム部門／DX推進部門から選出し、卒業生の中からピア・コーチを育成して自走化させる（Nadellaの「全社浸透」要件）。

---

## 5. 評価指標（KPI階層）

1. **第一指標（必達）**：Phase 0で合意した**現場KPI**の改善（例：検査工数▲X%、不良流出件数▲X件/月、設備停止時間▲X時間/月、需要予測誤差率▲Xpt、営業機会損失額▲X円）。
2. **第二指標**：`SKILLS/` への登録件数、および登録スキルの他部門への転用件数（3ヶ月以内）。
3. **第三指標（補助・診断用）**：卒業後3ヶ月・6ヶ月時点でのモデル・手法の**継続利用率**（定着率の直接測定。過去5年の教育がここで失敗していたため、今回は最重要の定点観測項目とする）。

参加率・満足度アンケートは実施してもよいが、成果報告・意思決定の材料には使わない。

---

## 6. パイロット計画

- 各部門1テーマずつ、計4テーマでパイロットコホートを実施（12週間）。
- パイロット終了後、第一指標の達成状況とテーマオーナーの評価をもとに、Jobsが次コホートへの継続投資可否を裁定する。
- パイロットの詳細な体制・予算・スケジュールは `00_STRATEGY/` のロードマップに統合する。
