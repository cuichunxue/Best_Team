# SKILLS/ 自動集積・横展開パイプライン
## STEP3: ENABLING の成果物（Nadella×Drucker）

`00_BOARD/RULES.md` §4「`SKILLS/` 自動蓄積方針」の実装手順。`02_SOLUTIONS/ai_action_learning_program/` のPhase 3から流入する成果物、および将来的な他の改革サイクルの成果物を、**他部門がオンデマンドで発見・利用できる状態**まで運ぶ一連の仕組みを定義する。

---

## 1. 設計思想（Not to doを含む）

- **登録の都度、Jobsのフル審議（STEP1〜4）を待たない**。それでは「自動集積」にならず、ナレッジが陳腐化するまで塩漬けになる。日常の登録は§3の軽量ゲートで回し、Jobsは月次で事後監査する。
- **「とりあえず置く」リポジトリにしない**。§3の5基準を満たさないものは`02_SOLUTIONS/`に留め置き、`SKILLS/`には昇格させない。
- **使い方だけを書いて終わらない**。「誰が・いつ・どのKPIをどれだけ改善したか」の実績と、「使うべきでないケース」を必ず併記する。

---

## 2. パイプライン全体像

```
[Capture]        [Curate]              [Package]        [Publish]         [Discover & Reuse]
Phase2完了時   →  Nadella/Drucker  →   _TEMPLATE      →  SKILLS/<名前>/ →  SKILLS/INDEX.md
成果の候補化      レンズで5基準判定       で成形            README.md         から検索・転用
                                                                              ↓
                                                                        利用実績を README に追記
                                                                       （フィードバックループ）
```

### Step 1｜Capture（候補化）
- `02_SOLUTIONS/ai_action_learning_program/` の各テーマで、Phase 2（現場実装・評価）終了時点のプロトタイプ・プロンプト・前処理ロジックのうち、テーマオーナーと伴走コーチが「他部門でも使えそうだ」と判断したものを候補にする。
- 候補は `02_SOLUTIONS/<テーマ名>/` に置いたまま、昇格候補フラグ（README冒頭に `## 昇格候補` セクション）を立てる。

### Step 2｜Curate（審査：軽量ゲート）
`00_BOARD/RULES.md` §4 の5基準をチェックリストとして、Nadella役（伴走コーチ）とDrucker役（テーマオーナーまたはKPI管理者）が共同で判定する。

| 基準 | 判定者 | 確認内容 |
|---|---|---|
| ①再現性 | Nadella役 | 別の工程・部門で試して機能したか（最低1件の実適用実績） |
| ②測定済み効果 | Drucker役 | Phase0で合意したKPIの改善が定量記録されているか |
| ③現地現物での検証 | Ohno役（現場検証パートナー） | 机上でなく実際の現場適用実績があるか |
| ④オンデマンド利用可能な形 | Nadella役 | 文脈を知らない他部門の担当者が読んで使える粒度になっているか |
| ⑤捨てる基準の明文化 | テーマオーナー全員 | 「使うべきでないケース」が具体的に書かれているか |

5基準を全て満たせば **即時公開可**。1つでも欠ける場合は `02_SOLUTIONS/` に差し戻し、欠けている基準を満たしてから再申請する。

### Step 3｜Package（整形）
- `SKILLS/_TEMPLATE/README.md` をコピーし、`SKILLS/<スキル名>/README.md` として作成する。
- プロンプト・コード・チェックリスト等の実体ファイルを同ディレクトリに格納する。

### Step 4｜Publish（公開）
- `SKILLS/INDEX.md` に1行追加する（部門横断検索のための唯一のカタログ）。
- 公開はNadella役・Drucker役の合議で即時実行してよい（Jobsの事前承認は不要）。ただし、事業戦略上のインパクトが大きい昇格（全社標準プロセスの変更を伴う等）は例外としてSTEP4（Jobsの最終裁定）を経る。

### Step 5｜Discover & Reuse（横展開）
- 他部門の担当者は `SKILLS/INDEX.md` を検索し、該当スキルの `README.md` を読んで自部門データに適用する。
- 適用した部門は、当該スキルの `README.md` 内「利用実績」セクションに、適用日・部門・得られた効果を追記する（登録者が更新し続ける必要はない、使った側が追記する運用とすることで負荷を分散する）。
- 3ヶ月ごとにNadella役が `SKILLS/INDEX.md` 全体を棚卸しし、利用実績のないスキルには「要検証」タグを付け、6ヶ月利用実績ゼロのスキルはJobsの月次監査で廃止候補として提示する（陳腐化したナレッジを積み上げ続けない）。

---

## 3. Jobsによる事後監査（月次）

日常の昇格判断は軽量ゲート（Step2）で回すが、Jobsは月次で以下を監査する。

1. 新規公開されたスキルが5基準を本当に満たしているかの抜き取り確認。
2. `SKILLS/INDEX.md` の利用実績トレンド（横展開が進んでいるか、それとも登録されただけで死蔵しているか）。
3. 廃止候補スキルの取り扱い決定。

この監査結果は `LOGS/` の月次サマリに記録する。
