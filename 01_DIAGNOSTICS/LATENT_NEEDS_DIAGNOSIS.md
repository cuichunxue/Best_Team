# LATENT_NEEDS_DIAGNOSIS.md
## 各部門の潜在ニーズ診断（STEP1: DEBATE）

**課題**：5年間、社内でAI（機械学習・深層学習／生成AIは対象外）教育を実施してきたが定着していない。現状、解析はメンバー各自がPythonでコーディングして行っている。
**診断対象部門**：製造／技術／生産技術／営業
**審議ステップ**：`00_BOARD/RULES.md` STEP1（DEBATE）＝ Musk・Ohno・Nadella・Drucker による独立診断→相互批判

---

## 0. まず疑うべきこと — 「教育が悪い」のではなく「教育が解いている問題が違う」

5年間の教育投資が定着しなかった時、最初に疑うべきは「教え方が下手だった」ではない。対象者は既にPythonでコーディングし解析できる人たちである。**スキルは足りている。定着しないのは、教育が現場の"本当に痛い場所"に接続されていないからだ**、というのが本診断のワーキング仮説である（Drucker：「顧客が求めていないものをどれだけ上手に作っても意味がない」の応用）。

> **重要な留保（Ohno要件）**：以下のマトリクスは、限られた情報から4者が第一原理で導出した**仮説診断**である。現地現物の原則上、これは検証前の作業仮説として扱い、`02_SOLUTIONS/` の実践伴走型プログラムの第一フェーズ（フェーズ0：現場実データ持ち込み）で、各部門の実データ・実案件と突き合わせて検証・修正することを必須とする。「机上の診断のまま展開する」ことは本ボードが最も嫌う失敗パターンである。

## 1. 4者の第一原理分解（診断レンズ）

| 視点 | 各部門の業務を分解する際の問い |
|---|---|
| **Musk**（第一原理・物理限界） | この判断・この解析は、理論上どこまで自動化・高速化できるか。今、何がそれを妨げている物理的・構造的制約か。 |
| **Ohno**（現地現物・ムダ排除） | この人は、実際に一日何にどれだけ時間を使っているか。手戻り・待ち・属人的判断はどこにあるか。 |

## 2. 部門別 対比マトリクス：表面上の悩み ⇔ 真の潜在ニーズ

### 2-1. 製造（現場・オペレーション）

| 表面上の悩み | 真の潜在ニーズ（恐怖／ボトルネック／構造的ロス） | 診断した視点 |
|---|---|---|
| 「AI研修を受けても、現場では使う機会がない」 | **恐怖**：AIが検査・良否判断を代替すると、自分たちの熟練の価値（＝評価・存在意義）が消えるという恐れ。「使わない」は能力の問題ではなく防衛反応。 | Nadella |
| 「Pythonなんて自分たちには書けない」 | **構造的ロス**：ベテランの良否判断基準（暗黙知）が言語化・データ化されておらず、モデルに翻訳する仕組みがない。問題は「コードが書けない」ことではなく「教える中身（現場の暗黙知）が形式知になっていない」こと。 | Musk / Ohno |
| 「忙しくて学ぶ時間がない」 | **ボトルネック**：データ収集・ラベリングの負荷がすべて現場に丸投げされ、成果（モデルの精度向上）を実感する前に離脱する。学習投資と成果実感の間のフィードバックループが長すぎる。 | Ohno |
| 「AIの結果が外れたら誰が責任を取るのか分からない」 | **恐怖**：予知保全・自動検査の誤判定が起きた際の説明責任の所在が未設計。責任構造がないまま「使ってみて」と言われることへの拒否反応。 | Drucker |

| 表面上の悩み | 真の潜在ニーズ（恐怖／ボトルネック／構造的ロス） | 診断した視点 |
|---|---|---|
| 「アルゴリズムの中身まで理解しないと怖くて使えない」 | **恐怖**：自分の専門性（材料工学・設計理論）がブラックボックスなモデルの前で無力化される、あるいは自分の仮説がデータに否定される恐れ。 | Nadella / Drucker |
| 「研究の片手間にやるには重すぎる」 | **構造的ロス**：実験データが個人のExcel・ローカルフォルダに散在し、前処理・特徴量エンジニアリングに毎回工数の大半を消費。同じ前処理を部門内で何度も再発明している。 | Musk |
| 「勉強会で習った手法と、実際に自分が持つデータのサイズ・質が合わない」 | **ボトルネック**：教育がアルゴリズム講義中心で、少数データ・ノイズだらけの実験データという技術部門特有の制約に対応した実践知が提供されていない。 | Musk / Ohno |
| 「自分がAIを使ったことが、評価にどう影響するか分からない」 | **構造的ロス**：技術部門のKPIは特許・設計品質であり、AI活用そのものは成果指標に組み込まれていない。「別腹の仕事」として扱われ、優先順位が上がらない。 | Drucker |

| 表面上の悩み | 真の潜在ニーズ（恐怖／ボトルネック／構造的ロス） | 診断した視点 |
|---|---|---|
| 「設備データはあるが、どう使えばいいか分からない」 | **構造的ロス**：ラインごとにセンサー仕様・データ形式・保存方法がバラバラで、標準化されていない。一つのラインで得た知見が他ラインに横展開できない構造。 | Musk / Nadella |
| 「研修で習った教師あり学習が、実際の異常検知には使えなかった」 | **ボトルネック**：異常事例（不良・故障）は本質的に希少（クラス不均衡）。標準的な教師あり学習の教え方と、生産技術が直面する現実のデータ特性がそもそも噛み合っていない。 | Musk |
| 「予知保全モデルを入れて外れたら、自分の首が飛ぶ」 | **恐怖**：モデルの予測精度に対する説明責任・評価基準が未設計のまま導入責任だけ負わされることへの回避行動。保守的判断が合理的選択になっている。 | Drucker |
| 「現場を止めてまでデータを取りに行く時間がない」 | **ボトルネック**：三現主義的なデータ収集（実際に現場で何が起きているかの一次情報）にかけるべき時間が、日常の保全業務に埋没している。 | Ohno |

### 2-4. 営業

| 表面上の悩み | 真の潜在ニーズ（恐怖／ボトルネック／構造的ロス） | 診断した視点 |
|---|---|---|
| 「AIって自分の仕事に関係ない」 | **恐怖**：需要予測・価格提案モデルが、自分が長年培った顧客との関係性・勘（暗黙知）を否定・代替するという脅威認識。 | Nadella |

## 3. 部門横断の共通真因（STEP2への引き渡し事項）

4者の相互批判の結果、以下3点が部門を問わず共通する構造的な真因として収束した。

1. **「操作研修」と「成果」が接続されていない（Drucker）**：5年間の教育はツールの使い方・アルゴリズムの説明に閉じており、各部門のKPI・評価制度に組み込まれていない。学んでも評価されず、評価されないから定着しない。
2. **暗黙知の形式知化という"本当にやるべき最初の一歩"が省略されている（Musk／Ohno）**：どの部門も「現場の判断基準・データが構造化されていない」段階でアルゴリズム教育に進んでおり、土台工事なしに建物を建てている。
3. **心理的安全性の設計が欠如している（Nadella）**：AI活用は多くの現場・担当者にとって「自分の価値が代替される恐怖」と表裏一体であり、この恐怖を正面から扱わない教育は本能的に拒否される。

**結論（STEP1→STEP2への引き渡し）**：解くべき本質的な課題は「AIの教え方」ではなく、「①現場の暗黙知・データを構造化し、②それを本人のKPIに直結する実案件で解かせ、③恐怖ではなく成果実感を通じて定着させる」という**伴走の設計**である。この結論は `02_SOLUTIONS/ai_action_learning_program/SPEC.md` の設計原則に直接反映する。
